Le but du projet est de comprendre, générer et valider le protocole

1. REFERENCE OPENAVRc ET ARCHITECTURE PROTOTHREADS

Les fichiers OpenAVRc étudiés sont PROTO_PCM.h et PROTO_PCM.cpp.

Le collègue de l’utilisateur a expliqué le principe de son moteur PCM :

1)  Construire la trame en interruption avec les Protothreads.
2)  Construire un train de bits/durées à émettre.
3)  Utiliser deux buffers :
    -   un buffer actuellement émis par l’ISR ;
    -   un buffer dans lequel la trame suivante est construite.
4)  A la fin d’une trame, échanger les buffers.
5)  L’ISR Timer1 programme les durées successives avec OCR1B.
6)  Le moteur PCM est commun aux PCM Futaba, Multiplex et, en principe,
    Graupner/JR.

Dans PROTO_PCM.h on trouve notamment les périodes : -
FUT_PCM1024_FRAME_PERIOD_US = 28500 us - GRA_PCM1024_FRAME_PERIOD_US =
44000 us - MPX_PCM256_FRAME_PERIOD_US = 57000 us

Le type de constructeur est de la forme : typedef
PT_THREAD((BuildRadioPcmBitStreamPtr)(struct pt ));

La structure PCM contient notamment : - le pointeur vers le builder ; -
les durées ; - deux tableaux StreamConsecBitTbl[2][…]; - un contexte
PtCtx persistant.

POINT CRITIQUE PROTOTHREADS : Les variables locales automatiques d’une
fonction Protothread ne sont PAS fiables au travers d’un PT_YIELD /
PT_WAIT. Toute donnée nécessaire après un yield doit être stockée dans
une structure persistante, ici PtCtx.

Cette règle a provoqué plusieurs des échecs des premières versions du
banc UNO.

2. REPRESENTATION DU FLUX DANS LE MOTEUR OPENAVRc

Le moteur PCM OpenAVRc ne stocke pas simplement 256 bits SPCM.

Il transforme le signal en une suite de durées entre transitions. Les
durées sont codées dans des nibbles, deux durées par octet. Le moteur
historique dispose de 44 octets, donc jusqu’à 88 durées.

L’ISR : - lit la prochaine durée ; - programme OCR1B relativement à la
précédente échéance ; - le matériel Timer1 bascule OC1B ; - à la fin du
buffer, échange les buffers et poursuit avec la trame suivante.

Principe important : OCR1B += durée et non : OCR1B = TCNT1 + durée

Cela évite d’accumuler la latence de l’ISR dans le timing du signal.

Sur Arduino UNO / ATmega328P : - Timer1 - prescaler /8 - horloge CPU 16
MHz - Timer1 = 2 MHz - 1 count = 0,5 us - sortie matérielle OC1B = PB2 =
Arduino D10.

Sur ATmega2560 / OpenAVRc : - OC1B = PB6 = Arduino Mega D12.

Le banc UNO utilise donc D10 pour reproduire le principe OpenAVRc.

3. STRUCTURE LOGIQUE SPCM 1024

Une trame logique comporte 32 quintets de 5 bits, répartis en quatre
groupes de 8 quintets.

Chaque groupe : - 6 quintets de données = 30 bits ; - 2 quintets = CTRL
10 bits.

Les 8 bits faibles de CTRL sont un CRC / contrôle calculé sur : - les
six quintets = 30 bits ; - les deux bits de poids fort de CTRL ; soit 32
bits protégés.

Polynômes CRC validés sur la capture MC-19 : - groupe A : 0x31 - groupe
B : 0x13 - groupe C : 0x91 - groupe D : 0x19

CRC : - MSB first - init = 0x00 - xorout = 0x00

Fonction de référence :

uint8_t spcmCrc8(const uint8_t data[4], uint8_t poly) { uint8_t crc = 0;
for (uint8_t n=0; n<4; n++) { crc ^= data[n]; for (uint8_t bit=0; bit<8;
bit++) { if (crc & 0x80) crc = (uint8_t)((crc << 1) ^ poly); else crc
<<= 1; } } return crc; }

Les quatre CTRL sont reconstruits ainsi : ctrl = ((ctrlHigh & 3) << 8) |
crc

Puis : qHi = (ctrl >> 5) & 0x1F qLo = ctrl & 0x1F

La vérification initiale sur la capture originale a donné 543 trames x 4
groupes = 2172 contrôles corrects.

5. MAPPING DES VOIES

Canaux 10 bits principaux : - CH1 = q16 * 32 + q17 - CH2 = q1 * 32 +
q2 - CH3 = q19 * 32 + q20 - CH4 = q4 * 32 + q5 - CH5 = q24 * 32 + q25 -
CH6 = q9 * 32 + q10 - CH7 = q27 * 32 + q28 - CH8 = q12 * 32 + q13

CTRL : - A = q6/q7 - B = q14/q15 - C = q22/q23 - D = q30/q31

CH9 a été validé matériellement : - voie 8 bits multiplexée AUX1/AUX3
; - q0 = nibble haut ; - q3 = nibble bas.

CH10 : - AUX2/AUX4 = q18/q21 ; - fallback AUX6/AUX8 = q26/q29 si les
premiers sont occupés. CH10 n’a pas été validé directement sur une
sortie physique car le récepteur utilisé ne possède que 9 sorties.

Ne pas inventer CH11/CH12 : leur fonctionnement n’a pas été établi.

6. FAIL-SAFE SPCM

Encodage Fail-Safe validé :

-   bit de contrôle AUX = 1 ;
-   AUX MSB = 1 => données Fail-Safe ;
-   AUX[3:2] = index du fragment 0..3 ;
-   AUX[1:0] = successivement FS3:2, FS5:4, FS7:6, FS9:8 ;
-   FS1:0 sont toujours zéro.

Référence :

uint8_t makeFailsafeAux(uint16_t fs10, uint8_t idx) { fs10 &= 0x03FC;
uint8_t fs8 = fs10 >> 2; return 0x10 | ((idx & 3) << 2) | ((fs8 >> (2 *
(idx & 3))) & 3); }

API recherchée pour la bibliothèque : setFailsafeUs(ch, us)
setFailsafeHold(ch) setFailsafeOff(ch) setAllFailsafeHold()

FS=0 dans l’API signifie HOLD/OFF.

Le Fail-Safe a été validé matériellement sur le banc : - voie normale
conservée pendant que le RF est présent ; - en perte RF, le récepteur
applique la position FS programmée.

8. TIMING SPCM MESURE

MC-19 : - période typique mesurée : environ 44,025 ms ; - capture
récente : environ 44,02536 à 44,02538 ms ; - jitter de l’ordre de 0,5 us
; - SYNC HIGH environ 414 à 415 us.

Tick SPCM : - environ 166,4 us.

Problème sur AVR : Timer1 travaille en demi-microsecondes. 166,4 us =
332,8 counts Timer1. Cette valeur n’est pas entière.

Il est donc faux de coder chaque tick comme 333 counts en permanence :
cela crée une erreur systématique.

La solution validée est un accumulateur fractionnaire.

9. ACCUMULATEUR FRACTIONNAIRE AVR

Référence V10.7b :

static uint16_t GraTickBase = 332U; static uint32_t GraTickRem =
8000000UL; static uint32_t GraTickFrac = 0;

static inline uint16_t GraNextTickCounts(void) { uint16_t c =
GraTickBase; uint32_t f = GraTickFrac + GraTickRem;

if(f >= 10000000UL) { f -= 10000000UL; ++c; }

GraTickFrac = f; return c; }

static uint16_t GraTicksCounts(uint8_t ticks) { uint16_t n = 0;
while(ticks–) n += GraNextTickCounts();

return n; }

Cela produit la bonne moyenne de 332,8 counts par tick.

L’accumulateur est remis à zéro au début de la trame / SYNC dans V10.7b.

Le train de transitions représente exactement 260 ticks SPCM : 260 *
332,8 = 86528 counts Timer1.

SYNC : environ 415 us = 830 counts.

La branche validée conserve aussi une compensation empirique de fin de
trame : (SPCM_FRAME_US - 68 us) * 2

Cette compensation ne doit PAS être supprimée simplement parce qu’un
accumulateur fractionnaire est utilisé. Une tentative antérieure l’avait
supprimée et avait régressé.

if(code == 0) { GraTickFrac = 0; half_us =
US_TO_PROTO_TICK(SPCM_SYNC_US); } else if(code == 15) { half_us =

Calcul du reste :

const uint32_t frameCounts = (SPCM_FRAME_US - 68UL) * 2UL;

const uint32_t exactUsedCounts = 830UL + 86528UL;

uint32_t rest = (frameCounts > exactUsedCounts) ? frameCounts -

11. COMPARAISON RECENTE UNO / MC-19 AU RETOUR

Configuration de Fail-Safe clarifiée par l’utilisateur : - seul C1 est
actuellement configuré pour aller à 1000 us en Fail-Safe ; - les autres
voies ne doivent pas être utilisées comme indicateur visuel de la sortie
FS.

Capture UNO : le générateur reprend immédiatement son émission après la
coupure observée. Les trames sont valides. C1 normal est transmis
normalement. Les fragments FS1=1000 restent correctement annoncés dans
le cycle AUX/Service.

Cela indique que le générateur lui-même ne reste pas “bloqué en
Fail-Safe” : le Fail-Safe est une consigne envoyée au module/récepteur,
pas un remplacement de la valeur de voie normale dans chaque trame.

Capture MC-19 : une différence de démarrage a été observée : après une
interruption, la MC-19 présente environ 40,05 ms d’état fixe avant le
début du véritable train SPCM.

Exemple observé : - SPCM arrêté vers 4,321616 s ; - reprise électrique
vers 6,978285 s ; - environ 40,051 ms d’état fixe ; - véritable train
SPCM vers 7,018336 s.

Cette observation a motivé V10.8.

AUCUN changement volontaire dans : - CRC ; - mapping des voies ; - table
Service ; - Fail-Safe ; - builder logique ; - double-buffer ; -
accumulateur fractionnaire ; - timing de trame V10.7b après démarrage.

IMPORTANT : ce test n’a d’effet que si le UNO / générateur redémarre.

Si l’utilisateur coupe uniquement l’alimentation du module HF en
laissant le UNO fonctionner, le UNO ne sait pas que le module HF vient
d’être réalimenté. Il ne rejouera donc pas automatiquement les 40 ms de
préambule.

Pour tester correctement cette V10.8 dans sa forme actuelle : démarrer
UNO + HF ensemble.

Si l’on veut reproduire ce comportement lors d’une simple remise sous
tension du HF sans redémarrer le UNO, il faudra fournir au UNO une
information “HF ON” (entrée GPIO, commande, détection de tension via
circuit adapté, etc.) et déclencher explicitement la séquence de
resynchronisation.

13. POINT ELECTRIQUE A NE PAS OUBLIER

Le module HF Graupner n’est pas seulement sensible au protocole
numérique.

Signal SPCM original : environ 0..10 V.

Le banc utilise un transistor BC547 pour l’adaptation de niveau.

Schéma de principe :

             +10 V
               |
             4,7 k
               |
               +------ SPCM vers module HF
               |
               C

GPIO – Rb — B BC547 E | GND ———–+—— GND HF

Le transistor inverse logiquement le GPIO.

Alimentation auxiliaire du module HF : la MC-19 fournit une broche
nominalement “+6 V”.

Découverte importante : avec l’alimentation de laboratoire limitée à
environ 60 mA, beaucoup de bruit RF autour de ~35 MHz apparaît sur le
SPCM et le fonctionnement devient erratique.

Avec une limite de courant de 20 mA : - le fonctionnement devient
nettement meilleur ; - la tension réelle s’écroule autour de 3,43 V ; -
commandes et Fail-Safe fonctionnent ; - la reprise peut être de l’ordre
de quelques secondes.

Ne pas conclure pour l’instant si le paramètre déterminant est : - la
limite de 20 mA elle-même ; - la tension réelle ~3,43 V ; - ou l’effet
de cette alimentation sur l’étage RF.

C’est encore à caractériser.

Résistance de base : - 4,7 k testée ; - environ 7,96/8 k obtenue par
association de résistances ; - 8 k fonctionne lorsque l’alimentation
auxiliaire HF est limitée à 20 mA.

Les essais électriques doivent être faits sans modifier simultanément le
logiciel.

14. ECHELLE DES VOIES — POINT A REVERIFIER

Fail-Safe.

16. REGLES POUR LA SUITE

1)  Ne pas repartir de V10.7 ou V10.7a.
2)  Conserver V10.7b intact comme référence.
3)  Traiter V10.8 comme une expérience de startup.
4)  Ne changer qu’un paramètre à la fois.
5)  Toujours vérifier les modifications avec l’analyseur logique.
6)  Comparer les captures UNO avec la MC-19, pas seulement le mouvement
    des servos.
7)  Ne pas supprimer la compensation -68 us sans nouvelle preuve.
8)  Ne pas remplacer l’accumulateur fractionnaire par un simple arrondi
    à 333 counts.
9)  Dans les Protothreads, ne jamais dépendre d’une variable locale
    automatique après un yield.
10) Pour OpenAVRc, conserver le principe double-buffer + OCR1B relatif.
11) Ne pas attribuer automatiquement un délai de reprise au protocole :
    le module HF et son alimentation auxiliaire ont déjà montré une
    forte influence.
12) Ne jamais brancher directement le signal SPCM ~10 V sur une entrée 5
    V/3,3 V ou un analyseur logique non protégé.

17. PROCHAINE EXPERIENCE RECOMMANDEE

Tester V10.8 avec UNO + HF démarrés ensemble.

Comparer : - temps d’acquisition initial ; - entrée en Fail-Safe ; -
retour de Fail-Safe ; - répétabilité sur plusieurs cycles.

Si le délai reste identique, revenir à V10.7b et considérer le préambule
40 ms comme non déterminant.

Pour étudier une remise sous tension HF pendant que le UNO reste allumé,
il faut idéalement : - une deuxième voie d’analyseur logique indiquant
le moment HF ON, avec adaptation de niveau sûre ; ou - une entrée dédiée
au UNO pour déclencher une séquence de resynchronisation.

Ensuite comparer image par image / trame par trame : - MC-19 avant HF
OFF ; - MC-19 premières trames après HF ON ; - UNO mêmes instants ; -
phase Service/AUX ; - CRC ; - C1 normal ; - fragments FS1 ; - période et
SYNC.
