# Graupner/JR SPCM 1024 Port to ESP32

## 1. Objective

The purpose of the ESP32 work was to reconstruct a **Graupner/JR SPCM
1024** signal compatible with a genuine Graupner RF module and its
receivers, using a fully software-generated and instrumentable
implementation.

This version served as the reference for understanding the protocol
before porting it to the AVR ATmega2560. In particular, it made it
possible to validate the frame structure, C1 to C8 channel encoding,
additional C9/C10 channels, the service-field cycle, and Fail-Safe
operation.

## 2. SPCM Frame Structure

A logical frame consists of **32 five-bit quintets**, arranged as four
groups of eight quintets.

Each group contains six data quintets and two control quintets. The
eight main channels are encoded with 10-bit resolution.

The validated mapping is:

-   C1 = q16 × 32 + q17
-   C2 = q1 × 32 + q2
-   C3 = q19 × 32 + q20
-   C4 = q4 × 32 + q5
-   C5 = q24 × 32 + q25
-   C6 = q9 × 32 + q10
-   C7 = q27 × 32 + q28
-   C8 = q12 × 32 + q13

C9 and C10 are additional channels encoded on **8 bits**. They use
available AUX fields in the service cycle.

In the SPCM20 format studied here, there are no equivalent C11/C12
channels.

## 3. Servo Value Conversion

Servo values used by the program are expressed in microseconds. They are
converted to the SPCM representation before the frame is built.

C1 to C8 use the protocol's 10-bit resolution. C9 and C10 use an 8-bit
value derived from the SPCM value.

This distinction was important during testing: C9 was verified with the
available receiver, which only has nine channels. C10 is therefore
generated by the program but could not be physically verified on this
receiver.

## 4. Physical Encoding

Logical quintets are converted into physical patterns using the 32-entry
SPCM lookup table.

The resulting physical frame is then converted into timed transitions
forming the signal sent to the RF module.

Logic-analyzer tests confirmed correct frame repetition and timing
intervals consistent with the measured SPCM tick.

## 5. CRC

The four frame groups use the following CRC polynomials:

-   Group A: `0x31`
-   Group B: `0x13`
-   Group C: `0x91`
-   Group D: `0x19`

The calculation is performed MSB first, with zero initialization and
zero final XOR.

This part was validated before the AVR port and did not need to be
reconsidered during the latest tests.

## 6. Service Fields and Fail-Safe

The ESP32 implementation made it possible to understand the role of AUX
fields in Fail-Safe transmission.

An AUX value with bit 4 set to 1 carries part of the Fail-Safe value.
Bits 3:2 select the transmitted fragment, while bits 1:0 successively
carry fragments of the value.

The Fail-Safe value is quantized so that bits 1:0 remain zero.

A zero Fail-Safe value means **HOLD/OFF**.

The validated build order is:

1.  load the service fields;
2.  insert Fail-Safe fragments into the relevant fields;
3.  insert C9/C10 when the AUX field remains available;
4.  insert C1 to C8;
5.  calculate the CRCs;
6.  convert to the physical frame.

This organization allows C9/C10 and Fail-Safe to coexist.

## 7. Test Commands

The ESP32 development version included a console allowing channels to be
modified directly and the protocol to be tested independently of
OpenAVRc.

A `SWEEP` mode automatically varies C1 to C8. This proved particularly
useful for visually confirming that received frames are actually being
refreshed and that the receiver is not simply locked onto a fixed frame.

Fail-Safe commands allow the position of each C1 to C8 channel to be set
individually, a single channel to be returned to HOLD, or all channels
to be returned to HOLD.

## 8. Fail-Safe Validation

Fail-Safe behavior was verified on the real hardware.

While a Sweep was running, cutting the link power caused the receiver to
move to the programmed Fail-Safe positions. When power was restored,
reception resumed immediately.

This validation was important because it provided a reliable reference
for the ATmega2560 port.

## 9. Role of the ESP32 Version

The ESP32 version should be regarded as the **functional protocol
reference** used to stabilize:

-   the 32-quintet format;
-   C1 to C8 mapping;
-   C9/C10;
-   CRCs;
-   the service cycle;
-   Fail-Safe encoding;
-   test tools, especially `SWEEP`.

The ATmega2560 port therefore did not reinvent the protocol. Its purpose
was to reproduce the same behavior with timing generation suited to the
AVR architecture and, ultimately, OpenAVRc integration.
